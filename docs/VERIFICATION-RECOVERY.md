# 验证失败后的登录恢复修复

2026-11-06，本地修复后已随 `20261106-163811-mvp-safety` 部署腾讯云服务器，详见 [部署记录](TENCENT-DEPLOYMENT.md)。本文不是滑块自动通过或免人工的实现声明。

## 当前现场

本地新账号页面已显示每日答题 5/5。没有为测试强行重复触发答题，也没有待处理的真实验证码。此前旧账号查分事件提示登录失效或平台拒绝；不能把重新扫码成功、已有满分或隔离测试通过当成滑块已解决。

## 根因

`loginflow.js` 在扫码确认及身份查询后调用积分接口，但用 `.catch(() => null)` 吞掉异常。即使积分接口返回 401/403、429 或需人工验证，后续仍执行 `upsertUser()`，覆盖凭据、增加登录代次并删除原来的自动任务暂停，最终对前端发送登录成功。

这会让被平台拒绝的会话恢复自动任务，违背已有的风险停止约定。

## 最小修复

让积分查询异常进入现有登录失败分支；在确认查询成功前不更新账号、不解除暂停、不发送成功事件，也不自动重试。正常扫码和有效积分查询成功时，仍按原流程绑定账号并恢复计划。

网络错误同样使本次扫码失败，需要检查后重试扫码；这是恢复条件收紧，不能把它描述为只改代码格式、完全没有失败路径变化。已有账号和原凭据保留，不增加网页密码或新的权限。

## 回归证据

新增 `app/test/loginflow.test.js`，使用隔离临时数据库和模拟官方响应：

- 六种失败：401、403、429 同时包含 timeout、需人工验证、无效积分数据、网络错误。
- 失败保留旧凭据、登录代次和验证暂停，每次只查询一次，不发送 done。
- 正常路径仍更新凭据与积分、增加登录代次、清除暂停并发送 done。

修复前六种错误均被标成 done，回归失败；移除吞异常后通过。最终 `npm test` 50/50 通过，`node test/flow.smoke.mjs` 端到端通过，未操作真实验证码。
